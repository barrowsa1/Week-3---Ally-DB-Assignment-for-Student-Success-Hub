## README for Assignment 3

For this project, I designed and made a prototype data model for a university’s Student Success Hub. This hub lets advisors see a quick picture of each student’s support history and tracks the student’s ID, name, email, and their program/major. Additionally, it holds their advising notes and the support visits information, which includes many different fields. The advising notes hold information regarding notes from the student’s advisor, the date of the visit, the advisor’s name, and what category the visit fell under. The support visits section holds the users' tutoring center visits, writing center appointments, or workshops attended, along with the date that they attended the following service, and a short notes description. From this hub, the university wants to be able to look up specific students and their corresponding data, run queries about all of the students, and draw analytics from the student population.

For my relational design, I made three different tables, Student, AdvisingNote, and SupportVisit, with primary and foreign keys to keep the data organized and consistent.The Student table and AdvisingNote table are connected through StudentID as AdvisingNote.StudentID references Student.StudentID. Also Student table and SupportVisit table are connected as SupportVisit.StudentID references Student.StudentID. The AdvisingNote and SupportVisit tables also have their own unique primary ID’s along side their foreign keys of StudentID to make sure that each advising note and support visit can be tracked and individually referenced. Using these primary and foreign keys helps keep the data consistent and supports a clean schema, as 
data must be inserted according to the correct format.

For my MongoDB design, I created one collection under Student and chose to embed the AdvisingNotes and SupportVisits in it. I designed it this way so that all the information for the student is in one place under the student collection. Instead of using StudentID to connect them across separate tables or collections, the information can all be easily accessed and edited depending on how it is used. With this in mind, consistency within the system is harder to maintain as we gain more flexibility and easier editing access. This is one of the trade-offs between my relational design and my MongoDB design. 

The relational design feels strongest when wanting to make sure the data stays consistent across multiple systems and also stays clean. This is because the primary and foreign keys help keep the schema clean. Additionally, this makes it easy for the database to run queries as all the fields are properly maintained. However, the MongoDB design feels the strongest when being used on a daily basis for normal tasks, such as adding an advisor note or support visit. The users don’t have to worry about the system being down and can put in as much or as little information as needed. This is very useful but can cause problems as user’s might forget important information fields or create new random ones. Essentially, the relational design feels stronger when it comes to running queries and using the database for analytics. The MongoDB design feels strongest for practical everyday use for users. To fill in the gap with possible missing fields and the loose schema, for the MongoDB design, I would use validation rules to make sure all the correct fields are included and in the correct format. I would use application checks to make sure users are not adding unnecessary fields, and I would use cleanup scripts to find and fix inconsistent or missing information.
