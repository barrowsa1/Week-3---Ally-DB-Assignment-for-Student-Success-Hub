## Integrity and Trade-Off Reflection

In lesson one of this week's content, we learned that relational databases have a fixed schema, strong integrity, are great for transactional systems where correctness is critical, and are designed around SQL and ACID transactions. Meanwhile, NoSQL databases, such as MongoDB, have a flexible schema, relax stricter integrity and consistency in exchange for scale and availability, are great for large, changing systems, and often focus on simple operations. Whether you use one or the other of these systems depends on what you are asking from the database. Essentially, relational systems are more strict to guarantee consistency, while NoSQL systems are more flexible to handle a huge, evolving system. However, for NoSQL systems, it is up to the users to work harder to manage the integrity of the system.

As mentioned above, relational databases have a fixed schema and strong integrity, and this is due to the use of primary and foreign keys to help ensure that data is inputted properly and organized in a consistent manner. Meanwhile, NoSQL systems, such as MongoDB that we are using, do not have these same keys and constraints in place, which causes new risks to appear. For example, some users might forget to include a section of data, such as the user's email, and there is nothing in place to prevent the system from allowing the email to be left out or entered in the wrong format. Additionally, there is nothing preventing a user from adding a new field, such as middleName or dateOfBirth, or changing the way information is stored. This can cause the system to have a lot of gaps and inconsistent fields if users add or take away fields.

With this possible decrease in consistency, there is an increase in flexibility, as our MongoDB can be easily edited and information can be added. As the CAP theorem for lesson 3 explains, distributed systems have to consider the trade-offs between consistency, availability, and partition tolerance when a network partition occurs. MongoDB's flexiblity gives us more freedom when adding or changing information, but this means that we need to be more careful about keeping our data consistent. To protect the integrity of our MongoDB system, I would make sure to incorporate some rules when inputting data into the system. For example, I would use validation rules to make sure all the correct fields are included and entered in the correct format. I would also use application checks to make sure users are not adding unnecessary fields or incorrect information. Finally, I would use cleanup scripts to find and fix inconsistent or missing data. This would still allow the system to have the flexibility that we want while also making sure our system stays accurate and consistent.
